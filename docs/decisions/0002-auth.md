# ADR 0002: Own magic-link authentication, local checkpoint

- Status: Accepted for local development; production readiness pending
- Date: 2026-09-15

## Decision

Keep the planned application-owned magic-link authentication. No external identity provider or new email service is required for local development. A trusted database operator provisions organizations and email memberships through `scripts.provision_user`; the web application cannot create memberships or accept an organization ID during login.

Links contain 256 bits of randomness, expire after 15 minutes, and are bound to the requesting browser's random HttpOnly cookie. The confirmation GET displays a form without consuming the link; a CSRF-checked POST atomically deletes the matching unexpired credential and creates a session. The database stores SHA-256 digests of link and session credentials, not their raw values. Sessions expire after eight hours and logout revokes them. Session replacement revokes the previous browser session.

Cookies are HttpOnly, with Secure enabled for HTTPS origins. Session cookies are SameSite=Strict; the login nonce is SameSite=Lax to support top-level email-link GET navigation without consuming the token. HTTP is restricted to loopback development. State-changing authenticated forms require a per-session random CSRF token. Login forms require a browser nonce. Link requests return generic responses and have persistent fixed-hour limits of five per email and twenty per peer. These limits are a local baseline, not a production abuse-prevention service or a timing-side-channel guarantee.

Each session selects a database membership; every request rechecks it. Report history, creation, retrieval, and downloads derive the organization from that session, never from submitted tenant identifiers. Removing membership invalidates access immediately. Owner/member roles are stored but currently have identical report permissions. Login selects the first membership by organization UUID. The organization switcher lists only the user's memberships and requires CSRF validation; switching checks current and destination membership, rotates the session and CSRF token atomically, and preserves expiry. The source-organization audit record identifies the selected destination. A replayed or concurrently consumed old session cannot switch again.

Login, logout, operator provisioning, and successful export generation append audit records. SQLite and PostgreSQL trigger definitions reject row UPDATE/DELETE; the baseline migration also adds a PostgreSQL TRUNCATE guard. These do not protect against privileged database administrators or schema removal. Production database privileges and migration ownership require a separate hardening pass.

## Delivery and logging

The local transport writes links to randomly named files created with mode 0600 inside a directory created with mode 0700. Existing directory permissions are not changed. The mailbox is not served over HTTP and is not an email integration. Operators must protect this directory and remove obsolete messages as appropriate; expired links cannot authenticate.

An explicit SMTP mode supports provider-neutral authenticated delivery over verified STARTTLS or implicit TLS. Failures revoke the issued link and log only a generic operational event. There is no automatic retry or local fallback; SMTP acknowledgment is not proof of inbox delivery. Transport tests include a real local TLS/SMTP exchange; external provider acceptance requires operator-supplied credentials and sender verification. See the [email runbook](../runbooks/email.md).

The configured loopback public URL determines link destinations, not the request Host header. Confirmation query strings are removed from the shared ASGI scope before response-time access logging. The development command also disables Uvicorn access logs. Responses use no-store and no-referrer headers. Browser history, upstream proxy logs, and request-body logging can still expose credentials: do not enable such logging for these routes.

## Verification and remaining work

SQLite tests exercise expiry, replay, concurrent consumption, browser binding, session revocation, membership removal, CSRF, authenticated import/export isolation, cookie flags, query redaction, foreign keys, and audit mutation rejection. Existing unauthenticated workflow tests explicitly opt into demo mode.

Schema changes now run through explicit Alembic migrations, not application startup. Database-backed tests pass locally against PostgreSQL 16.15 and SQLite; CI is pinned to the same PostgreSQL release. Revision 0002 adds indexed expiration cleanup and preserves the original expiry of existing rate-limit buckets. `make cleanup-auth` deletes at most 1,000 expired rows per table per invocation, never audit history. Before deployment, verify least-privilege roles and add membership administration, provider-specific email acceptance, HTTPS/proxy configuration, and security acceptance testing. Remote access remains blocked. Existing demo snapshots are not reassigned to real organizations.
